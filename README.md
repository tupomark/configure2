# Практическая работа №2: граф зависимостей NuGet

Вариант 31, дисциплина «Конфигурационное управление».
Python 3.11+, только стандартная библиотека для получения зависимостей.

## Этап 1: конфигурация

```sh
./run.sh --package Serilog --version 4.0.0 --stage 1
./scripts/check_stage1.sh
python3 -m unittest discover -s tests -v
```

Прототип принимает `--package`, `--version`, `--repository`,
`--test-repo`, `--output`, `--max-depth`, `--exclude` и `--stage`.
По умолчанию используется NuGet V3 index; `--output` задаёт PNG-файл,
`--max-depth` задаёт глубину 0–100, `--exclude` задаёт подстроку фильтра.
Режим `--test-repo` требует локальный JSON и имя пакета от A до Z.
Программа выводит настройки в формате `ключ=значение`.
Ошибки параметров дают код завершения 2, ошибки выполнения дают код 1.

## Структура проекта

- `src/config.py`: функции `package_id`, `package_version`, `depth`,
  `nonempty`, `image_path`, `create_parser`, `validate_source`,
  `parse_arguments`;
- `src/main.py`: функция `main` и точка запуска приложения;
- `tests/`: модульные тесты;
- `scripts/check_stage1.sh`: локальная демонстрация этапа;
- `run.sh`: запуск программы.

Сборка не нужна: Python исполняет исходный код непосредственно.
Сгенерированные изображения, PDF, служебные файлы и настройки IDE
исключены из Git с помощью `.gitignore`.

## Этап 2: получение прямых зависимостей

```sh
./run.sh --package Serilog --version 4.0.0 --stage 2
./scripts/check_stage2.sh
```

NuGet V3 Service Index предоставляет ресурс `PackageBaseAddress`.
`NugetRepository` читает список версий и `.nuspec` указанного пакета.
`parse_nuspec` выделяет прямые зависимости из XML; `--framework`
позволяет выбрать точную группу целевой платформы.
`version_key`, `normalize`, `parse_bounds`, `satisfies`, `select_version`
проверяют версии и выбирают совместимую версию согласно диапазону.
`fetch_bytes` выполняет ограниченные по времени и размеру HTTP-запросы.

Проверка этапа 2 использует локальный HTTP-сервер и настоящий CLI:
пакет A версии 1 зависит от B, A версии 2 зависит от C, а зависимости
пакета B не выводятся как прямые зависимости A.

## Этап 3: рекурсивный обход DFS

```sh
./run.sh --package A --version 1 --test-repo \
  --repository examples/cycle.json --max-depth 3 --stage 3
./scripts/check_stage3.sh
```

`TestRepository` читает JSON вида `имя -> версия -> пары зависимостей`.
`GraphBuilder.build` выполняет рекурсивный DFS, ограничивает глубину,
отбрасывает имена с подстрокой `--exclude` без учёта регистра и сохраняет
замыкающие рёбра циклов. Если более короткий маршрут к общей вершине
появился после длинного, вершина раскрывается повторно на новой глубине.
`Graph` хранит узлы и рёбра, `graph_lines` показывает их текстом.

`examples/cycle.json` проверяет циклы и фильтрацию, `diamond.json`
проверяет повторное раскрытие вершины на более коротком пути.

## Этап 4: обратные зависимости

```sh
./run.sh --package B --version 1.0.0 --test-repo \
  --repository examples/cycle.json --stage 4
./scripts/check_stage4.sh
```

`build_test_universe` охватывает все версии всех пакетов JSON-репозитория.
`ReversedRepository` обращает рёбра графа, а `reverse_graph` повторно
применяет рекурсивный DFS этапа 3 к полученному направлению рёбер.
Если есть несколько версий целевого пакета, результаты объединяются.
`--reverse NAME` выбирает другую вершину внутри исследуемого графа.

**Ограничение NuGet V3:** реальный репозиторий не предоставляет глобальный
поиск пакетов-потребителей. Для настоящего NuGet выполняется обращение
рёбер только внутри графа, построенного от `--package`. Для локального
JSON рассматривается весь заданный тестовый репозиторий.

## Этап 5: визуализация D2 и PNG

```sh
./run.sh --package A --version 1 --test-repo \
  --repository examples/cycle.json --stage 5 --output output/cycle.png
./scripts/check_stage5.sh
./scripts/check_all.sh
./scripts/check_tests.sh
```

`to_d2` формирует текст графа на языке D2, `render_graph` сохраняет
`.d2` и вызывает установленную программу `d2` для создания PNG.
На macOS установить D2 можно командой `brew install d2`.
Если D2 отсутствует, исходный файл `.d2` сохраняется, но команда
возвращает ошибку вместо ложного сообщения об успехе.

**Важно:** `check_stage5.sh` использует временную имитацию CLI D2 и
проверяет передачу аргументов, создание D2 и заголовок PNG. Это
оффлайн-проверка интерфейса, а не проверка настоящего рендеринга D2.
Полная проверка реального D2 выполняется приведённым выше запуском
`--stage 5` после установки D2. Для настоящих пакетов и сравнения с
.NET SDK 8 использовать:

```sh
./scripts/check_real.sh
```

Скрипт сравнивает три пакета: `Serilog.Sinks.Console` версии 6.0.0,
`Serilog.Sinks.File` версии 6.0.0 и `Serilog.Formatting.Compact`
версии 3.0.0. Пары «пакет-версия» сравниваются с независимым выводом
`dotnet list package --include-transitive --format json`. Расхождения
записываются в `output/real/comparison.json`. Получение зависимостей
для собственной реализации выполняется только через HTTP API NuGet;
менеджер `dotnet` используется исключительно для независимого сравнения.

В сравнительном сценарии собственный анализ объединяет группы NuGet,
в то время как .NET SDK восстанавливает пакеты для целевой net8.0.
Причины возможных различий: NuGet restore применяет правила выбора
совместимых групп, транзитивного разрешения конфликтов, приоритет
прямых зависимостей и другие ограничения. Наш граф показывает
объявленные в nuspec пути, ограниченные выбранной глубиной.

## Сдача и ограничения качества

Исходники: `src/`, модульные тесты: `tests/`, примеры: `examples/`,
локальные сценарии: `scripts/`, запуск: `run.sh`.
Документация дополнена постепенно в пяти коммитах. Файлы PNG, PDF,
папки `output` и служебные данные не коммитятся. Отдельной сборки нет.
Локальные проверки запускаются без интернета; для настоящего NuGet
нужно соединение с сетью, для сравнения нужен установленный .NET SDK 8.

Преподаватель проверяет Conventional/Scoped Commits, структуру, строки
Python не более 80 символов, функции не более 40 строк и не более
7 аргументов, сложность не более 10, docstring и PEP 8.
